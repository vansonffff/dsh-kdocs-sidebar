## 0.4.3 — 2026-10-04

### 修复：右击一行时，那行的灰色悬停高亮消失

**症状（用户报）**：鼠标悬停在文件行上有灰色强调，一右击，强调就没了。

**先在真实浏览器里复现，再动代码**（Chromium + CDP 真实鼠标事件；探针留存于
`Agents/过程稿/kdocs-右键高亮-浏览器探针-20261004/`）：

| 观察（修复前） | 值 |
|---|---|
| 悬停时行背景 | `rgb(4,5,6)`（harness 里 `--dsw-alias-interactive-bg-hover` 的可辨识取值） |
| 右击后行背景 | `rgba(0,0,0,0)`，且 `···` 快捷按钮同时消失 |
| `elementFromPoint(行中心)` | **`menu-backdrop`** |

**根因**：菜单和一个 `position: fixed; inset: 0; zIndex: 49` 的全屏遮罩同一次提交挂上。
遮罩成为指针下的元素 → 行收到 `mouseleave` → 行的 `hover` 状态转 false。
**高亮消失不是"没渲染"，是那层遮罩把指针从行上拿走了**；它同时让菜单打开期间
面板里任何行都无法被悬停，并整块吞掉关闭菜单的那一次按键。

**改法**（`client.js`）：

1. `EntryRow` 增加 `active`：**菜单属于哪一行，哪一行就保留 hover 表面**（并保留 `···`）。
   面板把 `menuKey` 传给每一行，树/视图/搜索三处调用点一致。
   新增 `data-kdocs-row-active` 诊断属性。
2. **删除那层遮罩**，关闭改由 `document` 上的监听器承担，只在菜单打开期间安装：
   - `click`（capture）：**仍吞掉**关闭菜单的那一次点击（`preventDefault` + `stopPropagation`），
     行为与旧遮罩一致 —— 关闭菜单不会顺带打开下面的行；点击落在菜单内则原样放过；
   - `contextmenu`：落在另一行上就交给那行自己的菜单（旧遮罩会把这次右击吃掉），
     落在空白处则与旧行为一致地抑制平台菜单；
   - `keydown`：**Escape 关闭菜单**（旧实现没有键盘出口）。
3. 顺带修正同一区域两处 `jsx` 变参子节点（真实 runtime 的 `jsx(type, config, key)` 会**静默丢弃**
   表格配置之后的参数，工作区已记录过这个坑）：
   - 详情面板的标题 + 「关闭」：修复前渲染成一个**空 header div**，而那颗按钮是全包**唯一**的
     `setDetail(undefined)` —— 于是详情面板**根本无法关闭**；
   - 重命名草稿的「重命名 / 取消」：修复前只有输入框，没有任何按钮。

### 验证

- **`node --test test/*.test.js`：291/291**（原 285；新增 `test/context-menu-hover.test.js` 5 条，
  并在 `panel-interaction.test.js` 补 1 条详情面板 header + 2 处重命名按钮断言）。
- **负向对照**：同一套 Node 断言指向修复前的 bundle → **12 例中 7 例红**（含两条被丢弃子节点）；
  真实浏览器探针指向修复前 → **8/17**，指向修复后 → **17/17**。
- 探针的负向对照是**显式的**：`before` 模式下缺陷项必须失败，否则脚本自己 exit 1。

## 0.4.2 — 2026-10-04

### 变更

- **PDF 渲染移出本包**：桌面端「原版」的 PDF 查看器改由独立插件 **`dsh-pdf-viewer`**
  经 client 服务 `pdfViewer` 提供。本包移除 `client.pdf.js`、`vendor/pdfjs-*`、
  `scripts/build-pdf-chunk.mjs` 与 `src/client/pdf-viewer.js` —— 全应用只剩一份 pdf.js。
  缺少该插件时，PDF 面板渲染 `pdfViewerMissing`（中英双语）明确写出要装哪个插件，
  **不静默降级、不白屏**；状态在渲染期判定（`paneStatus`），不靠一次注定失败的导出。
- **PDF 里可以直接划选引用**：`client.js` 的 PDF 分支外包一层 `data-kdocs-pdf-area`
  并挂上与文本模式**同一个** `onReaderMouseUp`。新渲染器的文字层让画布上的文字成为
  真 DOM 文本，于是 `window.getSelection()` 直接可用，写入的 marker 与文本模式逐字节一致
  （>800 字仍只写引用头）。
- 新增文案 `pdfViewerMissing`（zh/en）。`package.json` 的 `files` 随之移除已删产物。

### 修复：PDF 文档的「原版」不再卡在「导出完成但没有下载地址」

真机实测暴露两个**先于本版就存在**（0.4.0 起）的问题，症状同一条报错
「导出完成但 kdocs-cli 未返回下载地址」：

1. **竞态**：`wps.query-export` 会在载荷还没就绪时就返回 `status='finished'` ——
   同一任务一次答 `{status:'finished', data:{}}`、下一次带回 `url`（实测 kdocs-cli 2.7.1）。
   旧代码在第一次 `finished` 就 `break` 并立刻抛错。现在**多等一次轮询**。
2. **PDF 源文件**：文档本身就是 PDF 时，`wps export --format pdf` 的每一次查询都是
   `finished` + 空 data，**永远不给地址**（实测：`新案件.pof` 两次运行、每次两轮，
   全部空载荷）。原文件的下载地址也走不通：`drive download-file` 给的是**需要鉴权的存储网关
   地址**（`ksc-bj.ag.wps.cn/api/object/…`，无签名参数，裸取 403），而本插件**绝不读取或转发
   reader 的 token**。`pdf extract-pdf-pages` 那条路会在云盘**新建文件**（副作用），也不采用。

因此：

- 面板按文档名识别「本身就是 PDF」（`.pdf`）→ **根本不发起导出**，直接给出文案
  `pdfSourceUnsupported`：说明原因，并指出两条可行路径（「文本」模式可读正文且同样可划选引用、
  「在金山文档打开」看原版）。
- provider：`finished` 空载荷**连续两次**即结束循环并抛出**可操作**的报错（约 4 秒，
  不再白等 90 秒超时）；同时新增 **PDF 魔数校验**，200 状态码的 HTML 错误页不再被当成文档
  送进渲染器。

> **更正（2026-10-04，同日）**：上面那条「面板按扩展名 `.pdf` 直接拦下、不发起导出」**已撤回**。
> 原因：那条实测用的是 `新案件.pof`，而 `pof` 并不在 `drive.read-file` 的支持列表里
> （CLI 原文：`Unsupported file type .pof (read_file supports docx / doc / wps / pdf / …)`）——
> 也就是说 `.pof` 与真正的 `.pdf` **不是同一类文档**，把 `.pof` 的"永远没有导出地址"
> 推广到 `.pdf` 是**未经证实的推断**。按扩展名一律拦下，风险是**挡掉一条本来可用的路**
> （用户那份 `.pdf` 很可能只是撞上了下面的竞态）。
>
> 现在保留的都是**实测支持**的部分：多等一次轮询（治竞态）、连续两次空载荷则快速给出可操作
> 文案、`%PDF-` 魔数校验。`.pdf` 是否真的没有导出地址，**尚未取得真实 `.pdf` 样本验证**；
> 面板不做猜测，一律按 CLI 的实际回答处理 —— 能导出就渲染，不能导出就给出那句话。
> 真 `.pdf` 的结论待补（需一个真实 `.pdf` 文档的 file_id）。

### 验证

- **284/284 测试通过**（`node --test test/*.test.js`）。新增/改写：
  PDF 区划选 → 浮层 → marker 与文本模式一致（含 >800 字只写引用头）、
  缺渲染器时状态为 `missing` 且 **exportPdf 一次都不发**（防止"导出没人能画的 PDF"）、
  本包不再携带任何 PDF chunk/pdf.js（文件不存在 + 源码无 `require.async('./client.pdf.js')`）、
  web（`http:`）树里没有 `data-kdocs-pdf-area`（负向对照）。
- 导出轮询新增独立套件（用替身 CLI + 本地 HTTP 服务，不碰真实凭据）：空载荷多等一次后成功、
  永久空载荷**快速**失败且文案可操作、非 PDF 载荷被拒、缓存生效。
  **负向对照**：把"第一次 finished 就放弃"打回原形 → 4/5 转红；去掉多等一次 → 相关用例转红。
- 跨插件服务通道用**真实 cordis** 探针验证：`ctx.reflect.provide('pdfViewer', …)` 后
  消费端 `ctx.inject(['pdfViewer'], cb)` 触发、`dispose` 后干净撤回。
- 渲染器自身的实测（虚拟化、文字层对齐、划选、回收、zoom）见 `dsh-pdf-viewer`：
  Node 32/32 + 真实 Chromium 17/17。
- PDF 修复用**真实 CLI** 端到端复核：PDF 源（`新案件.pof`）4 秒失败并给出可操作文案；
  普通 `.docx` 3 秒成功（163857 字节，`%PDF-` 头）。

### 边界

- 桌面端 PDF 预览**依赖 `dsh-pdf-viewer` 存在**。若本包要对外发布可用，需一并发布该插件，

- **金山 PDF 云文档（实测样本 `新案件.pof`）在桌面端「原版」拿不到导出地址**：每次查询都是
  `finished` + 空载荷。面板会在约 4 秒后给出可操作文案（「文本」模式 / 「在金山文档打开」）。
  真正的 `.pdf` 未取得样本验证 —— `.pof` 不在 `read-file` 支持列表内，两者不是同一类文档，
  结论不可互推。

## 0.2.6 — 2026-09-13

本版是**表现层迭代**：右栏从「功能完整的插件界面」做成「DSH 原生的云文档浏览器」，
并修掉了若干真实缺陷 —— 其中两个在**已发布的 0.2.0 里就会让用户踩到**。

**改动面很窄**：`src/` 与 0.2.0 **几乎逐字节相同**，唯一例外是 `src/tools.js`
里那两个工具输出契约的修复（见下）。Host、CLI 调用、资源协议、Agent 工具的能力面均未变化。

### ⚠️ 从 0.2.0 升级的人请先看这一条

**0.2.0 发布的 `kdocs_list` 与 `kdocs_search` 是坏的 —— 两个分页工具的输出契约都写反了。**

工具的 `output.schema` 会被编译成 JSON Schema，并对每次返回值做**致命校验**：
多一个未声明的字段、或少一个必填字段，都会抛 `INVALID_TOOL_OUTPUT`，
`render` 根本不会执行。0.2.0 的情况是：

| 工具 | 0.2.0 的声明 | 0.2.0 实际返回 | 后果 |
|---|---|---|---|
| `kdocs_list` | 要求 `pageCount` 必填 | `{ entries, total }` | **每一次列目录都失败**，空文件夹也一样 |
| `kdocs_search` | 把 `total` 声明为**必填** | `{ entries, pageCount }` | 没要云盘总数的搜索失败；**要了总数的仍然失败**（多带了一个未声明的 `pageCount`） |

也就是说：**如果你的 Agent 在 0.2.0 上一调用 `kdocs_list` / `kdocs_search` 就报错，那是这两个 bug，不是用法问题、也不是登录问题。** 升级到 0.2.6 即修复。

0.2.0 当时的测试没有任何一条检查过编译后的 schema，所以这两个契约断裂没被发现。
现在两个工具的返回值都会先过一遍 DSH 运行时的 schema 校验，
并把工具装进真实的 `ToolRuntime` 端到端跑一次。

### 新增

- **文件类型图标**：文件夹 / Word / Excel / PowerPoint / PDF / 文本 / 图片 / 通用，
  8 种字形，统一 16×16 包围盒，只使用产品自身的颜色 token。
  文件名认不出来的后缀一律落到「通用」——认不出来就该长得像文件，而不是像 Word。
- **行内快捷操作**：鼠标悬停或键盘聚焦文件行时，行尾出现 `···`，点击打开与右键相同的菜单。
  它绝对定位、不参与布局，所以**不会挤掉文件名**；宽度不足时仍可继续用右键，是渐进增强而非唯一入口。
- **键盘可达性与无障碍**：行、视图标签、菜单项都有 `focus-visible` 焦点环；
  图标按钮带 `aria-label`（如「更多操作：季度报告.docx」）；装饰性图标 `aria-hidden`；
  视图标签使用 `role="tablist"` / `aria-selected`。

### 改进

- **信息密度提升**：行高 29px → 24px，顶部工具区 118px → 89px。
  **同一屏可见文件从 23 行增至 30 行。**
- **顶部导航去胶囊化**：六个视图入口从 9 个带边框的胶囊改为纯文字 + 下划线选中态。
  附带修掉一个 0.2.0 就存在的缺陷：窄侧栏下视图标签会**换行成两行**（占 57px）；
  现在任何宽度都保持一行（核心控件不再从一行变两行）。
- **搜索区压缩**：`全部 / 文件名 / 正文` 从独占一行三个胶囊改为搜索框内的行内控件。
  **搜索能力一项未减**（三种范围全部保留），搜索逻辑一行未改。
- **右键菜单精修**：菜单项统一 28px 高，7 项按功能分成 3 组（两条 0.5px 极弱分割线），

### 修复

- **文件行悬浮导致整个面板变白**（本版开发期引入并当场修复）。
  行的快捷按钮引用了作用域外的翻译函数，鼠标一进入文件行就抛
  `ReferenceError`，抛在 React 协调子组件阶段，槽位运行时随即清空整个面板。
  **根因不是那一行，而是三处结构性漏洞**：测试的 React 替身让 `useState` 永远返回初值
  （该分支在 CI 里从未执行）、有一条断言只检查「源码里存在某段文本」（写坏的和写对的文本一模一样）、
  以及 `guarded()` 当时只是 `try/catch` 而非真正的 React 错误边界（子组件的错不经过它）。
  三个漏洞都已修复，并新增真渲染测试与变异验证。
- **搜索状态下点击视图标签，看到的是空搜索页而不是该视图**。
  视图数据其实已取回，但渲染仍走搜索分支。
- **文件夹重命名会丢掉 `.v1` 这类点后缀**。草稿按正则剥「扩展名」，
  但写回时只有文件才带扩展名可补 —— 于是 `案件.v1` 被改成 `案件`，**静默改掉你的文件名**。
  现在只对真正带扩展名的条目做剥离。
- **分页失败后无法重试**。视图与搜索的「加载更多」失败时会把游标丢掉，
  而该按钮只在有游标时渲染 —— 一次瞬时网络失败就再也加载不了，且无法恢复。
  现在失败时保留游标（首页失败仍清空）。
- **修复一条恒真的测试**：live 分页用例断言 `pages >= 1`，任何运行都通过；
  已收紧为 `> 1` 并追加「确实读到了首页之外的条目」。

### 内部质量（不改变行为）

- 测试 **207 → 252**，全部通过。
- 发布前做了一次全仓审查，含 **19 条承重测试的变异验证**：故意破坏实现，
  确认**恰好**相关测试失败 —— 未经变异验证的测试，其通过不构成证据。
  本次审查据此发现了下面「修复」一节里的前三个缺陷。
- 间距收敛到统一刻度（2/4/6/8/12/16），清掉了 `5px / 7px / 9px` 这类随手数值。

### 已知问题（本版未修，将在后续版本处理）

1. **`getLink` 失败时「在金山文档打开」/「复制链接」静默无反应**（应给出错误提示）。
2. **tab 标题组件没有错误边界**（面板主体已有）——标题抛错的后果是标签空白。
3. **预览组件的 effect 依赖了整个 props 对象**，依赖「座位引用稳定」这一假设才不出问题。
4. **无法解析的地址在「原版」模式下是一块白**（错误信息目前只在文本模式显示）。
5. **`unwrapData` 不检查内层 `code`**：若 CLI 返回嵌套错误信封，会被当成成功静默吞掉。
   该形状实测从未出现，但属于潜在风险。
6. **预览与标题组件仍无测试执行到**的部分：错误分支、划选引用、`needsLogin` 分支、
   详情/历史版本/批注结果渲染。
